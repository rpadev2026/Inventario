# Inventario del Restaurant

Sistema de inventario de insumos y materia prima: facturas de compra → Bodega Central → solicitudes de insumos a otras bodegas con aprobación y recepción.
Stack: Next.js (App Router, TypeScript) + Tailwind + Supabase (Postgres). UI en español.

## Comandos
- `npm run dev` / `npm run build` / `npm start`
- `npm test` — Vitest: validadores, esquemas y funciones SQL (migraciones ejecutadas en PGlite, sin necesitar Supabase)
- `npx tsc --noEmit` — chequeo de tipos
- `npm run seed:admin -- <rut> <correo> <clave>` — crea el administrador inicial (requiere `.env.local`)
- Instalar dependencias siempre con `--legacy-peer-deps`.

## Arquitectura
- Toda la lógica corre en el servidor (server actions). El navegador nunca habla con Supabase; el servidor usa `service_role` (`lib/db/supabase.ts`, solo servidor). Las tablas tienen RLS activo sin políticas públicas.
- `app/(app)/<modulo>/` páginas + `actions.ts` (módulos: compras, proveedores, productos, bodegas, solicitudes, movimientos, usuarios, mantenedores); `lib/auth/` sesión, hash y login; `lib/services/` reglas de negocio y correo; `lib/validation/` Zod y RUT.
- Las operaciones críticas son funciones SQL transaccionales en `supabase/migrations/` (`registrar_factura`, `anular_factura`, `crear_solicitud`, `actualizar_solicitud`, `aprobar_solicitud`, `cambiar_estado_solicitud`, `recepcionar_solicitud`). No reimplementar esa lógica en la app: llamar al RPC.
- Las migraciones se ejecutan en orden `0001`…`0021` + `seed.sql` (`0006` maestros y FK por código, `0007` permisos de roles y RPC `guardar_rol`, `0008` tablas de territorio, `0009` datos oficiales generados, `0010` proveedores/sucursales por código + trigger de jerarquía, `0011` índice único parcial: un RUT de vendedor vigente en un solo proveedor, `0012` un rol base inactivo se puede guardar y reactivar; sigue prohibido desactivar uno vigente, `0013` Productos con `"IdProducto"` y costo unitario base: ver «Productos»; `0014` mensajes de los RPC con el producto como «código — nombre» vía `etiqueta_producto`, `0015` historial de precios de compra y `registrar_factura` con precios que ya incluyen IVA, `0016` precio y costo desde la factura: el producto tiene solo `"UnidadBase"` ingresada y las líneas de factura llevan su `"UnidadMedida"`; `0017` no se desactiva una unidad que es base de productos o unidades vigentes, y `registrar_factura`/`anular_factura` bloquean las filas de los productos; `0018` el código y el nombre de un producto se guardan siempre en MAYÚSCULA por el trigger `normalizar_producto`, y `productoSchema` también los convierte, `0019` módulo Recetas: tablas `Recetas`/`RecetaDetalles`, triggers de reglas, RPC `guardar_receta` y `calcular_receta` y permisos `recetas.*`: ver «Recetas», `0020` catálogo de permisos en la tabla `"Permisos"`: ver «Permisos y mantenedores», `0021` ajustes de Recetas: los guardados que validan ciclos se serializan con `pg_advisory_xact_lock`). Cambios de esquema = nueva migración numerada, y actualizar `supabase/tests/db.test.ts`.

## Permisos y mantenedores
- La autorización es por PERMISO, no por nombre de rol. El catálogo vive SOLO en la tabla `"Permisos"` (`Codigo`, `Modulo`, `Descripcion`, `Orden`; migración `0020`; `RolesPermisos."Permiso"` la referencia por clave foránea y `guardar_rol` rechaza un código desconocido con «Permiso desconocido: x»), no en TypeScript: `lib/services/permisos.ts` (`cargarPermisos`) la lee para la matriz de roles y `lib/auth/permisos.ts` solo trae la lógica (`permisosEfectivos`, `tienePermiso`, `agruparPermisos`). Un permiso nuevo = una fila en `"Permisos"` (migración) y listo; `supabase/tests/permisos.test.ts` revisa que cada código usado en `requerirPermiso`, `requerirPaginaPermiso`, `tienePermiso`, el menú y los avisos exista en la tabla (no hay chequeo de tipos). Permisos actuales: `compras.ver|registrar|anular`, `proveedores.ver|gestionar`, `productos.ver|gestionar`, `recetas.ver|gestionar`, `bodegas.ver`, `solicitudes.ver_propias|crear|gestionar`, `movimientos.ver`). `leerSesion` lee `RolesPermisos` en cada petición (no van en el token) y calcula los efectivos con `permisosEfectivos` (el Administrador recibe todos los de la tabla `"Permisos"`).
- Server actions: `requerirPermiso(...)`; páginas: `requerirPaginaPermiso(...)` (alguno de los permisos basta). Pantallas solo-Administrador (usuarios, mantenedores y crear/editar bodegas; ver bodegas es el permiso `bodegas.ver`): `requerirAdmin` / `requerirPaginaAdmin`; NO son asignables por permiso. Administrador tiene todos los permisos de forma implícita (sin filas en `RolesPermisos`).
- Mantenedores (solo Administrador): `/mantenedores` (índice), `/mantenedores/formas-pago`, `/mantenedores/unidades-medida`, `/mantenedores/formatos` (`components/app/catalogo-admin.tsx` + `catalogo-form.tsx`) y `/mantenedores/roles` (matriz de permisos; guarda con el RPC `guardar_rol`; los 4 roles base `EsBase` no se renombran).
- Territorio (solo Administrador): `/mantenedores/regiones`, `/mantenedores/ciudades` y `/mantenedores/comunas` (mismo `catalogo-admin` con padre opcional; códigos CUT inmutables; no se desactiva un padre con hijos vigentes). «Ciudad» = Provincia (la jerarquía oficial es Región → Provincia → Comuna; no existe lista oficial de ciudades). Datos de la API DPA del MOP (SUBDERE) generados con `npm run gen:territorio` → `0009_territorio_datos.sql` (la API trae 345 comunas; se agrega Antártica 12202). En Proveedores/Sucursales `Region`, `Ciudad` y `Comuna` guardan CÓDIGO (FK + trigger `validar_territorio`); formularios con `components/app/selector-territorio.tsx` (tres combobox dependientes), lógica pura y validación de jerarquía en `lib/territorio-opciones.ts`, carga/verificación en servidor en `lib/services/territorio.ts`.
- Formas de pago, unidades de medida y formatos se guardan por CÓDIGO (FK a `FormasPago`/`UnidadesMedida`/`Formatos`), nunca como texto; los nombres se resuelven al mostrar (`lib/catalogo-nombres.ts`, `lib/catalogo-opciones.ts`).
- Factura (`/compras/nueva`): cada línea lleva producto, «Unidad de medida» (por defecto la unidad base del producto; solo unidades de su misma familia), precio y cantidad; el precio unitario de cada línea YA INCLUYE IVA («Precio unitario (IVA incl.)»): total = suma de líneas, neto = round(total / 1,19), IVA = total − neto (`lib/factura-calculo.ts`, mostrado en el formulario y validado en Zod y en `registrar_factura`: el detalle debe sumar el total, ±$1); `ComprasDetalle` guarda precio y total de línea con IVA. Folio solo enteros; precio hasta 2 decimales; fecha de recepción ≥ fecha de factura. Se valida en Zod y también en SQL (`registrar_factura`).
- Crear proveedor/producto desde la factura: enlaces `?volver=/compras/nueva` (ruta validada con `lib/volver.ts`, nunca redirige fuera del sitio); el borrador de la factura se guarda en `sessionStorage` (`lib/borrador-factura.ts`) y se restaura al volver, preseleccionando lo recién creado (`aplicarPreProducto`).
- Paginación: `lib/paginacion.ts` (`paginar`: 10 por defecto; 10/25/50/75/100; estado en la URL) y `components/app/paginador.tsx`. Bodegas (`/bodegas`): listado con filtro por nombre (sin tildes) y estado (`lib/bodegas-filtro.ts`, `?q&estado&pagina&tam`); `filtros.tsx` filtra mientras se escribe (300 ms) y conserva el botón Buscar; `?ver=ID` (bodega y productos, `?ppagina&ptam`), `?editar=ID` y `?crear=1` (solo Administrador) son vistas aparte con botón Volver que conserva página y filtros; al guardar/crear vuelven al listado con un aviso que se difumina (`components/app/aviso.tsx`, `?aviso=`). Tablas con `table-wrap-sticky` tienen scroll propio y la fila de títulos fija.
- Productos (`/productos`): mismo patrón que Bodegas. Clave `"IdProducto"` (bigint); `"Codigo"` opcional y único (vacío = null), `"Nombre"` único; ambos siempre en MAYÚSCULA (sin distinguir mayúsculas en los únicos). El producto tiene UNA sola unidad, `"UnidadBase"`, que se ingresa al crear (solo entre unidades base: factor 1, p. ej. Gramo, Mililitro, Unidad) y NO se edita si ya tiene stock, facturas, solicitudes o movimientos (trigger `validar_producto_unidad_base`; la acción conserva la guardada). NO existe precio de compra en el producto: `"CostoUnitarioBase"` (numeric(14,6), nullable, **con IVA**, por unidad base) lo escriben solo `registrar_factura` (`round(precio de la línea / Factor de la unidad de la línea, 6)`; rige la última factura registrada) y `anular_factura` (vuelve al costo de la última línea de factura no anulada, o null). Cada cambio de costo queda en `"HistorialPreciosProducto"` (`IdCompra`, `Origen` Compra|Anulación, precio y unidad de la línea, costo anterior/nuevo, `Anulada`, usuario); «Ver» lo muestra paginado (`?hpagina&htam`) con enlace a la factura. El stock mínimo/crítico se guardan en unidad base pero se escriben en cualquier unidad de la familia (selector junto al campo; `lib/unidades.ts`: `unidadesBase`, `unidadesDeFamilia`, `convertirABase`; `cargarUnidades` en `lib/catalogo-nombres.ts`). Las tablas hijas (`ComprasDetalle`, `BodegaCentral`, `StockBodega`, `SolicitudesDetalle`, `MovimientosBodega`) usan `"IdProducto"`; stock, solicitudes y pantallas trabajan en la unidad base (`BodegaCentral`/`StockBodega` reciben `round(cantidad × Factor, 3)`; `ComprasDetalle` guarda precio, unidad y cantidad tal cual se ingresaron). Los RPC reciben `{"producto": <id>, ...}` (`producto_de_item` valida) y la factura `{"producto","unidad","precio","cantidad"}`: la unidad de la línea debe ser vigente y de la misma familia (misma `UnidadBase`) que la base del producto. Selectores muestran `lib/producto-etiqueta.ts` («código — nombre» o solo el nombre). Rutas `?ver=ID`/`?editar=ID` (un id inválido se ignora). `UnidadesMedida` lleva `"UnidadBase"` (FK por código) y `"Factor"`: KG→G ×1000, L→ML ×1000, G/ML/UN base ×1; una unidad base tiene factor 1 y no se encadena; no se puede cambiar base/factor de una unidad que usan productos o líneas de factura (trigger `validar_unidad_medida`); el mantenedor de unidades pide «Unidad base» (vacía = ella misma) y «Factor» (decimales con coma; «1.000» se rechaza por ambiguo). Filtro por código/nombre y estado (`lib/productos-filtro.ts`, `components/app/filtros-listado.tsx` compartido con Bodegas, `lib/filtro-estado.ts`), listado paginado, `?ver=ID` (datos + costo + stock por bodega + historial), `?editar=ID` y `?crear=1` (requieren `productos.gestionar`; la acción del servidor lo exige igual) como vistas aparte con Volver y aviso. Con `?volver=/compras/nueva` abre directo Crear y, al crear, vuelve a la factura con el producto elegido.
- Recetas (`/recetas`): mismo patrón que Productos (listado paginado con filtro por código/nombre y estado en `lib/recetas-filtro.ts`; `?ver=ID`, `?editar=ID` y `?crear=1` como vistas aparte con Volver y aviso; crear/editar requieren `recetas.gestionar`, ver `recetas.ver`; el rol Compras recibe ambos por la migración). `"Recetas"`: `"IdReceta"`, `"CodigoReceta"` (opcional, único) y `"Nombre"` (único), ambos en MAYÚSCULA (trigger `normalizar_receta` y `recetaSchema`), `"RendimientoPorciones"` y rendimiento opcional con unidad (`"RendimientoCantidad"` + `"RendimientoUnidad"`, ambos o ninguno; sin rendimiento no se puede usar como sub-receta). `"RecetaDetalles"`: producto O sub-receta, `"Cantidad"` (veces que entra), `"PorcionNeta"` (lo que aporta cada una, en `"UnidadMedida"` de la misma familia que la base del producto o del rendimiento de la sub-receta) y `"PorcentajeMerma"` (fracción: 0,25 = 25 %; en el formulario es un porcentaje de 0 a 1000 % con 2 decimales; porciones de la receta: hasta 2 decimales y 999.999,99). Fórmula: bruto = `Cantidad × PorcionNeta × (1 + merma)`; costo de línea = bruto convertido a unidad base × `CostoUnitarioBase` (o, en sub-receta, × costo total ÷ rendimiento en unidad base). «Ver» y el formulario marcan «(parcial)» el costo cuando falta algún ingrediente, y el producto muestra en cuántas recetas se usa. El formulario no ofrece como sub-receta a las recetas que ya contienen a la editada (`lib/receta-arbol.ts`). El costo NO se guarda: lo calcula `calcular_receta` (recursivo, tope 20 niveles, jsonb) y la vista previa del formulario usa la misma fórmula en `lib/receta-calculo.ts`. Un ingrediente sin costo deja la línea «sin costo» y la receta «incompleta». Reglas en SQL (triggers): sin ciclos (ni consigo misma), sin ingredientes repetidos, no se desactiva una receta usada como sub-receta por una vigente, no se cambia a otra familia el rendimiento de una sub-receta en uso, y no se cambia base/factor de una unidad ni la unidad base de un producto usados en recetas. Se guarda con el RPC `guardar_receta` (reemplaza todos los detalles en una transacción) desde `guardarReceta` (`app/(app)/recetas/actions.ts`).
- Proveedores (`/proveedores`): mismo patrón. Filtro por RUT/razón social/giro y estado (`lib/proveedores-filtro.ts`), listado paginado, `?ver=ID` (solo lectura: datos, sucursales y vendedores), `?editar=ID` (formulario del proveedor + listados de sucursales y vendedores con «Editar» y «Agregar»; cada uno se edita/crea en una vista aparte `&sucursal=ID|nueva` / `&vendedor=ID|nuevo` con Volver, y al guardar regresa a la edición del proveedor con aviso) y `?crear=1` (requieren `proveedores.gestionar`). Al guardar el proveedor vuelve al listado con aviso. `/proveedores/[id]` solo redirige a `?editar=ID`. Con `?volver=/compras/nueva` abre directo Crear y vuelve a la factura con `?proveedor=ID`. Reglas: el RUT de un vendedor puede repetirse en otros proveedores pero vigente en uno solo (`lib/vendedor-rut.ts`, validado en `guardarVendedor` para dar un mensaje claro, y respaldado en la BD por el índice único parcial `un_vendedor_rut_vigente`); TODO correo que se ingresa usa la regla única de `lib/validation/correo.ts` (`esCorreoValido`, `MSG_CORREO`) en el servidor y `components/app/campo-correo.tsx` en el formulario: proveedores, sucursales, vendedores, alta de usuarios (`lib/validation/usuario.ts`), login y `seed:admin`.
- Usuarios (`/usuarios`, solo Administrador): mismo patrón. Filtro por RUT/nombre/correo y estado (`lib/usuarios-filtro.ts`), listado paginado con roles en solo lectura, `?ver=ID` (solo lectura), `?editar=ID` (datos: nombres, apellidos, correo y estado vía `guardarUsuario`/`editarUsuarioSchema`; el RUT no se modifica; sección Roles con Quitar/Agregar inline) y `?crear=1`. Nadie puede desactivarse a sí mismo ni quitarse el rol Administrador. `resetearClave` existe en `actions.ts` pero no tiene pantalla. Duplicados: «El RUT ya está registrado» / «El correo ya está registrado».
- Mantenedores (`/mantenedores/*`, solo Administrador): mismo patrón en los 6 catálogos (`components/app/catalogo-admin.tsx` genérico, `lib/catalogo-filtro.ts`) y en Roles (`lib/roles-filtro.ts`). Listado con filtro por código/nombre (y padre) y estado, paginado; `?ver=` (en catálogos incluye «Dónde se usa» con las cantidades de `cargarUso`/`UsoCfg` en `lib/services/catalogo.ts`), `?editar=` y `?crear=1` como vistas aparte con Volver y aviso. Roles: el estado de un rol base vigente está bloqueado; uno base inactivo se puede reactivar desde Editar.
- Buscadores: `components/app/combobox.tsx` (accesible) con `lib/buscar.ts` (normaliza tildes/mayúsculas); entradas numéricas con `lib/numeros.ts` (`filtrarDecimal`, `parseCantidad`, `parseDecimal2`).

## Diseño de la aplicación ("Pizarra y esmeralda", Flat)
- Generado con la skill ui-ux-pro-max (estilo Flat; Poppins para títulos/botones + Open Sans para texto). Modo claro por defecto y oscuro automático (`prefers-color-scheme`). Sin sombras ni degradados. **Única excepción aprobada:** el fondo animado de la pantalla de ingreso (`components/app/fondo-shader.tsx`, `MeshGradient` de `@paper-design/shaders-react`, versión exacta fijada porque la 0.0.x puede romper compatibilidad), con la paleta de la marca (pizarra y esmeralda, hex copiados de `tema.css` porque el shader no lee variables CSS), movimiento `speed = 1` y quieto (`speed = 0`) con `prefers-reduced-motion`. Si el rendimiento no es bueno, bajar `SPEED` a 0 en ese archivo. Solo se usa en el login; el resto de la aplicación sigue sin degradados.
- Todo el estilo vive en `app/tema.css` (variables `--surface`, `--text-muted`, `--primary`... y clases semánticas). Las pantallas NO usan colores Tailwind sueltos: usar `card`, `btn btn-primary|secondary|danger`, `input`, `table-wrap`+`table`, `link`, `pill`, `badge`, `alert`, `page-title`, `section-title`.
- Formularios: siempre etiqueta visible con `components/app/field.tsx` (`<Field label="...">`), nunca solo placeholder. Rejillas: `form-grid form-grid-2|3|4` y `fld-2|fld-3|fld-full` (NO llamarlas `col-N`: Tailwind v4 tiene `col-N` y le gana). Líneas de detalle: `line-grid line-grid-3|4` (apiladas en celular).
- Estados: `components/app/badge.tsx` (punto + texto; el color nunca es la única señal). Tonos: ok, warn, danger, info, neutral.
- Navegación: barra lateral oscura en ≥1024 px; en pantallas menores barra superior + barra inferior con máx. 5 destinos (4 + «Más» con hoja). Íconos SVG de trazo en `components/app/icon.tsx` (sin emojis).
- Controles de 44 px, foco visible, respeta `prefers-reduced-motion`. Tablas con scroll horizontal en pantallas estrechas.

## Reglas que no hay que romper
- Autorización: cada server action llama `requerirPermiso(...)` o `requerirAdmin()` (`lib/auth/session.ts`), que revalida usuario, roles y permisos contra la BD. No confiar en el token ni en ocultar botones. `requerirRol`/`requerirPagina` ya no existen.
- Roles base: Administrador (todo, implícito), Compras, Bodeguero Central, Solicitante; el Administrador puede crear más roles con la matriz de permisos. El rol no autoriza por su nombre (salvo Administrador): lo hacen sus permisos.
- Nadie aprueba ni rechaza su propia solicitud; solo el solicitante edita, envía y recepciona la suya (reforzado también en SQL).
- Validar toda entrada con Zod; mostrar al usuario solo mensajes de negocio (código `P0001` de las funciones SQL), nunca errores crudos de la BD.
- Contraseñas: argon2id, política de 12+ caracteres, historial de las últimas 5. Nunca texto plano ni logs de claves.
- Las consultas con relaciones anidadas hacia `Usuarios` deben indicar el nombre de la FK (`Usuarios!Tabla_Columna_fkey`): `Solicitudes`, `HistorialSolicitudes` y `UsuariosRoles` tienen varias.
- Next.js aquí es una versión nueva: `middleware` se llama `proxy.ts`; consultar `node_modules/next/dist/docs/` ante dudas.
